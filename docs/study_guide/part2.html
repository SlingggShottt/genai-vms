4. The pipeline, station by station

Now we open each box of the big picture. The order is the order the video travels. Remember the rule that explains the design: heavy things (video, pictures) sit in storage; only small notes with links travel between services.

4.1 Cameras and MediaMTX — getting the video in

Cameras speak a protocol called RTSP (a way to stream video over a network). We do not have a building full of cameras, so a camera simulator plays recorded datasets as if they were live RTSP cameras (it uses ffmpeg). We replayed real footage from public research datasets (MEVA bus-station cameras, UCF-Crime clips) this way.

MediaMTX is the media server in the middle. It receives each stream and re-publishes it two ways: WebRTC (very low delay, used for the live wall) and HLS (chopped into small files, used for playback in a browser).

Think of it as…A TV broadcasting hub. Cameras are the studios; MediaMTX is the control room that re-broadcasts each channel in two formats: live (WebRTC) and on-demand (HLS).

4.2 Ingestion — cutting the tape into envelopes

  1. There is one asynchronous worker per enabled camera. The list of cameras comes from the API (and falls back to a config file); it is refreshed every 60 seconds, so adding a camera needs no restart.
  2. ffmpeg copies the stream into 10-second MPEG-TS files without re-encoding (so it costs almost no CPU).
  3. Each file is uploaded to the MinIO bucket vms-segments; one picture per second (a keyframe) goes to vms-keyframes.
  4. It publishes a small Kafka message segment.v1: camera, segment id, start and end time in UTC, and the storage link.
  5. If the stream drops it reconnects with exponential waiting (1, 2, 4… up to 30 s) and the next message is flagged gap_before = true, so nobody mistakes a gap for silence.
Be honest about…The 30-minute, 6-camera "no missing segment" stress test was written but never run as specified. Shorter real runs and the "restart workers mid-stream" chaos test passed (chapter 9).

4.3 Kafka — the post office

Kafka is a message system. A producer writes a message to a topic; any number of consumers read it at their own speed. Because the queue sits between services, a slow GPU service never slows the one before it, and if a service crashes it simply resumes where it stopped.

  • Messages carry links, not video (and must stay under 1 MB). This was decision D-02.
  • Every topic name ends in a version (.v1). A message format may only gain optional fields; anything else needs a new version and a new topic. These formats are the contracts between Divyansh's and Jatin's code; each has a Python class (Pydantic) and a sample file (fixture).
  • Consumers follow one rule: validate, write idempotently, then commit. "Idempotent" means doing it twice gives the same result as doing it once, so a replayed message cannot create duplicates.
  • A message that keeps failing goes to the dead-letter topic (vms.dlq.v1) instead of blocking everything. There is a tool to inspect and replay it.
Think of it as…A post office with labelled pigeonholes. The clerk who cuts the tape drops a note into the "segments" hole saying "parcel at shelf 12, camera 3, 10:15:00". The detective collects notes from that hole when ready; the clerk does not wait.

4.4 Perception — writing the report card (the digital twin)

Perception is the first AI step. For every 10-second segment it:

  1. Samples frames (2 to 5 per second) from the video.
  2. Detects objects with YOLO11: what is in the picture and where (a bounding box), for people, cars, bags and so on.
  3. Tracks them with ByteTrack: the same person in consecutive frames gets the same id (like cam03-t412), even across segment boundaries. The tracker state is checkpointed in Redis so a restart continues the numbering.
  4. Adds attributes (colour of clothes), the zone the object is in (polygons an admin draws on each camera: e.g. "staff doorway"), and motion (speed, direction).
  5. Computes a SigLIP 2 embedding: a list of numbers that captures what the object looks like, used later for "find things like this".
  6. Writes it all as the digital twin JSON, stores it in MinIO and announces it on Kafka.
Think of it as…A detective who watches each 10-second envelope and fills in a standard form: "3 people, 1 backpack; person #412 in a red top stayed 47 seconds in the staff doorway". Later, everyone reads the form, nobody re-watches the tape.
Why a "lightweight" twin?The research paper builds a heavy twin for every frame (segmentation plus depth). That is impossible live on 4 GB. We keep a small twin (boxes, tracks, attributes, zones, vectors) and draw detailed object outlines (masks) only on demand for search results. Measured: both perception models together use only about 966 MB of GPU memory.

4.5 The storage trio (plus Redis)

Beginners often ask "why four databases?" Because each is good at one job:

  • MinIO speaks the same language as Amazon S3. It is for big files and gives each a link. Locally it is free; in the cloud it can be swapped for real S3.
  • PostgreSQL is the classic relational database: exact facts you can filter and join ("all high-severity events on cam02 yesterday").
  • Qdrant is a vector database: it stores the "meaning vectors" and finds the closest ones. It also supports hybrid search (by meaning and by exact words).
  • Redis is a fast scratchpad: the GPU lease, response cache, live-push channel, rate limits.

4.6 The indexer — filing the report card

The indexer listens to the twin, event and incident topics and files everything: segments, tracks and counts into Postgres; frame and track vectors into Qdrant; event captions and incident-report sections into the knowledge collection (two search indexes at once: a dense one for meaning and a BM25 one for exact words). It is idempotent, so replaying a message changes nothing.

4.7 The events service — rules plus a second opinion

The six rules (config/rules.yaml)

RuleFires when…Severity
intrusion.restricteda person/vehicle is seen in a zone marked restricted for at least 2 sampled frameshigh
intrusion.after_hoursa person is seen in a zone outside its allowed hours (zones can have a schedule)high
loiteringa person stays in a zone for 60 s or moremedium
crowdingmore than 8 people in a zone for 20 smedium
abandoned_objecta bag stays still 30 s and its owner has been away 20 shigh
runninga person moves faster than a speed threshold (0.35 frame-widths per second) in at least 3 sampleslow

Rules look at consecutive twins, so one long episode becomes one candidate, not a hundred (the rule engine folds consecutive hits and debounces them). Thresholds live in a config file, not in code.

The VLM gate

A VLM (vision-language model) is an AI that can look at pictures and talk about them. Our gate sends up to 4 keyframes of the candidate to qwen2.5-VL 3B (running locally through Ollama) and asks for structured JSON: a verdict (yes / no / unsure), a confidence, and a one-sentence caption. The result is one of:

  • verified — published as an event and becomes an alert (if severe enough);
  • rejected — stored with its reason (useful for measuring the gate), never published;
  • skipped — the model could not be asked (or the rule has verification off); published but flagged unverified.
A real result worth quotingOn a replay of real bus-station footage (MEVA), the rules raised 49 candidates and the gate judged all 49. It verified 30 of 30 loitering candidates in the waiting room, but rejected all 9 "restricted-doorway intrusion" candidates (people were just walking past) and rejected 2 of 4 abandoned-object candidates. That is the gate earning its keep: it removes false alarms that rules alone would have sent to the operator.
Be honest about…Those figures come from one 10-minute replay with zones drawn by hand. The gate's precision and recall against labelled clips was not measured (that needs labelled data). Also, 31 of the 37 verified alerts were waiting-room loitering: a rules-tuning problem, not an AI problem.

4.8 Alerts

The API consumes verified events and creates one alert per event (severity at least medium by default; lower ones are stored and searchable but do not interrupt anyone). Each alert is pushed to every dashboard through a WebSocket the moment it is created. Notification channels (dashboard, email, Telegram) are plugins; only the dashboard is on, by team decision. Actions are audited (who acknowledged what, with their note).

4.9 Correlation — connecting the dots across cameras

A single camera sees only part of the story. The camera topology is a small map an admin draws: which cameras overlap (two views of one area) and which are linked by transit (walking from A to B takes between a minimum and maximum number of seconds). The correlation service links events on different cameras if (1) their event types are compatible (a matrix in config/correlation.yaml), (2) the cameras are connected, and (3) the times fit once a tolerance is added. Chains of links are merged into groups with union-find.

Think of it as…Friend groups. If A knows B and B knows C, then A, B and C are one group, even if A never met C. Events on different cameras become one "story" the same way.

A group stays open while linked events keep arriving and closes after a quiet period, which is the signal for the reasoning service. If two groups turn out to be one, they are merged: the oldest survives and absorbs the rest. A hard rule: an event is in at most one live group.

Be honest about…Correlation uses time and the camera map only. It does not recognise that the same person appears on two cameras (person re-identification is future work, decision D-10). So in busy scenes it can over- or under-link.
